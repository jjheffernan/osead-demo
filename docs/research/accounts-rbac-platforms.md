# Research: agent vs. guest accounts + RBAC in coastal / vacation-rental / brokerage platforms

Research pass for the accounts-rbac feature (see `docs/research/accounts-rbac-feature.md`). Goal: catalog how real vacation-rental brands and brokerage CRM/portal products separate **agent/staff** accounts from **consumer/guest** accounts, what each role can actually do, and how "book externally" handoffs work — so OSEAD's `admin | user` demo-account contract can grow into `admin | agent | guest` without owning a calendar, a CMS, or a DB.

**Existing OSEAD contract** (do not rebuild): `src/lib/demo-account.ts` defines `DemoRole = "admin" | "user"`, a `sessionStorage`-backed `DemoAccount`, and `roleForEmail()`/`isDemoAdminCredentials()` gates against one hardcoded demo admin. `/login` + `/register` post to `functions/api/{login,register}.ts` (shape-validate, rate-limit, log, return `202` — no password hash, no user table, explicitly marked `ponytail:` for a future Auth.js/Clerk swap). `/account` branches three ways on `readDemoAccount()`: signed-out gate, plain-user welcome panel, or the full `AdminShell.svelte` island for the one admin email. `src/config/staff.ts` already has a `StaffMember[]` seed (id/name/role/bio) used by the About page — this is the natural seed for an `agent` roster.

## Executive summary

- **Every brand in this space keeps a hard wall between the operator/agent side and the consumer side — usually two logins, two subdomains, two apps.** Twiddy runs a public guest login on `twiddy.com`, a homeowner portal, and a separate `ops.twiddy.com` staff login with its own "looking for Guest Services portal?" escape hatch. Vacasa splits into a homeowner portal/app and a guest reservation flow. kvCORE is the one exception — agent backend and consumer-facing IDX site share one login, because the "consumer account" *is* the agent's website, not an independent identity.
- **Consumer roles are almost always "lite" — save, ask, track — never transact.** Across Twiddy (trip boards, saved favorites, pre-reserve), Vacasa (reservation details, door codes, support tickets), RealScout (saved/dismissed listings, saved searches, message-agent), and Compass One (buyer collections, tour requests, document access), the guest/buyer/renter role never issues a charge or signs a contract *in the portal itself* — that always routes to a lease e-sign, a payment processor, or an agent-mediated offer. This maps directly onto OSEAD's "booking stays external" constraint: the account layer's job is context + continuity, not the transaction.
- **Agent/staff roles are built around a lead/inventory pipeline, not content editing.** kvCORE, Follow Up Boss, BoomTown, Sierra Interactive, and Real Geeks all center the agent's home screen on **assigned leads** (via round-robin, geographic routing, or a claimable "pond") plus **saved/behavioral signals** on those leads (viewed listings, saved searches, showing requests) — not a CMS-style "edit the site" surface. That's the correct shape for OSEAD's `agent` role: an inbox + an inventory slice, not admin-shell parity.
- **"Continue booking externally" is a solved, well-documented pattern with three tiers of maturity**, all reusable without owning a calendar: (1) **query-string deep links** that pre-fill dates/guests/property on an external booking engine (Mews, Skipper, WPRentals' Affiliate Link field, Flip.to's token-templated URL) — zero auth, zero backend; (2) **magic links** (single-use, short-TTL emailed tokens) for passwordless re-entry to a saved session — a UX pattern, not a booking-specific one; (3) **SSO/token handoff** (SynXis Booking Engine's CRM-Login API: brand site gets an `access_token`, POSTs it as a hidden form field to the booking engine's landing URL) for brands that want a signed-in guest to land pre-authenticated on a third-party engine. OSEAD's realistic ceiling this wave is tier 1 (deep link) with tier 2 (magic link) as the "if we add outbound email" upgrade — tier 3 needs a real IdP contract with a specific booking vendor, which is explicitly out of scope.
- **The single loudest "don't copy" signal across every brokerage-CRM review**: kvCORE/BoomTown/Sierra/Follow Up Boss all ship the *lead pipeline + IDX* combo, but every third-party review (Luxury Presence, InboundREM, US Tech Automations) independently flags the same failure mode — template-driven IDX pages produce **duplicate content across every agent using the platform**, the CRM automation requires real setup investment before it pays off, and "one-stop" backend dashboards trade simplicity for a steep learning curve. None of this is a fit for a demo template; OSEAD should keep the agent surface to "my inbox + my inventory," not attempt IDX/MLS parity or marketing automation.
- **Net for OSEAD:** extend the existing `sessionStorage` + `DemoRole` contract with two more literal roles (`agent`, `guest`), keep `staff.ts` as the agent identity seed, add a small guest-side "saved homes + inquiry history" local-storage shape (mirrors `demo-account.ts`'s own pattern), and implement "continue booking" as a deep-link URL builder (property slug → query string) with a documented magic-link stub for later. No new backend, no new roles-matrix framework, no IDX.

## Role capability matrix

Capabilities actually observed in the exemplars below, not aspirational. "✓" = a real, documented feature; "—" = not offered by that role in that product; "n/a" = role doesn't exist in that product.

| Capability | Admin / ops (Twiddy Ops, kvCORE broker, Compass admin) | Agent / staff (Twiddy homeowner-facing team, kvCORE agent, Follow Up Boss user, Real Geeks agent) | Guest / consumer (Twiddy guest, Vacasa guest, RealScout homebuyer, Compass One client) |
| --- | --- | --- | --- |
| Saved / favorited listings | n/a (manages others') | View team-wide saved activity as a signal (kvCORE behavioral tracking, RealScout live activity feed) | ✓ — trip boards (Twiddy), Collections (Compass), Interested/Uninterested (RealScout) |
| Saved searches + alerts | n/a | Set up / monitor alerts on a client's behalf | ✓ — RealScout "My Searches," listing alerts |
| Inquiry / lead inbox | Team-wide visibility, reassignment | ✓ — core surface: Smart Lists (FUB), Lead Pond / Round Robin claim (Real Geeks), Activity Feed (kvCORE) | Submits inquiries; sees own thread only |
| Assigned inventory / "my listings" | Full inventory + reassignment | ✓ — a filtered slice (own leads, own listings) via round-robin/geo routing | n/a |
| Messaging agent/client | Oversight | ✓ — two-way texting/email (FUB), messaging tab (RealScout) | ✓ — "Message your agent" (RealScout), chat thread (Compass One) |
| Reservation / transaction status | Full visibility | Visibility into own deals' stage | ✓ — own reservation only (Vacasa), own transaction timeline (Compass One) |
| Documents (lease, disclosures, closing docs) | Full access | Upload/share on client's behalf | ✓ — signed lease via e-sign (Twiddy), documents library (Compass One) |
| Financials (statements, payouts, revenue) | Brokerage-wide | Own commission/pipeline only (not modeled in any exemplar as agent-visible payout data) | ✓ **owner-only** — Vacasa homeowner revenue dashboard/1099s (not a renter-guest feature) |
| Site content editing | ✓ (AdminShell equivalent) | — (Web & IDX tab is config, not raw content editing) | — |
| Book / pay | — (facilitates, doesn't transact) | Facilitates (send quote, draft offer) | — **always hands off** to lease e-sign, payment processor, or external booking engine |

**Reading this for OSEAD:** the `admin` role you already have maps to the left column (keep `AdminShell` as-is). The gap is the middle and right columns — `agent` needs an inbox + an inventory filter, `guest` needs saved listings + inquiry history + a document/status stub. Neither role needs money, contracts, or content editing in this wave.

## Exemplar notes with URLs

### Vacation-rental brands (guest ↔ homeowner/staff split)

**Twiddy & Company** (Outer Banks) — [Guest payments/login](https://www.twiddy.com/outer-banks/guests/payments/) · [Advance Property Hold (guest account)](https://www.twiddy.com/guestadvancehold/) · [Twiddy app](https://www.twiddy.com/app/) · [Property management / homeowner portal](https://www.twiddy.com/outer-banks/property-management/) · [Twiddy Ops Portal](https://ops.twiddy.com/#/)
Three distinct surfaces: (1) a **guest account** on the main site/app for signing the lease electronically, paying rent/deposits, viewing reservation details, and pre-reserving next year's week ("Advance Property Hold" — a first-come-first-served window that opens the Tuesday after departure); (2) a **homeowner portal**, built in-house, exposing investment/performance data (separate audience from guests, not staff); (3) a staff-only **Ops Portal** at a dedicated subdomain (`ops.twiddy.com`) with its own login and an explicit "Looking for Guest Services Portal Log-In?" link back to the consumer side — a clean, low-tech pattern for keeping ops staff off the guest-facing domain entirely. The mobile app adds a **group feature**: guests can build a shared "trip board," invite the rest of their travel party, and vote on favorites before the leaseholder books — a multi-user pattern worth noting for a "guest" role that isn't always a single person.

**Vacasa** — [Homeowner account overview](https://www.vacasa.ca/homeowner-guides/vacasa-homeowner-account) · [Homeowner app](https://www.vacasa.com/homeowner-app) · [App Store listing](https://apps.apple.com/us/app/vacasa-homeowner/id1572325511)
Vacasa's account split is **owner vs. guest**, not agent vs. guest (Vacasa's field staff don't get a customer-facing portal identity in what's publicly documented) — still useful as the clearest "capability list" of any brand surveyed. Owner account/app: revenue dashboard (real-time), full booking calendar with guest-privacy redaction (first name + last initial + party size only), self-service "reserve your own stay," year-end tax documents (1099-MISC/1042-S) gated behind a **second login step** even after the app's persistent session ("step-up" reauth for financial data — worth copying conceptually), direct-deposit payout setup, local property-manager contact card, and guest review visibility. Notably the app explicitly requires re-entering credentials to view the Account/tax tab even though the rest of the app stays logged in — a concrete, low-effort step-up-auth example for any future OSEAD financial view.

**Bluegreen Vacations** — [Owner sign-in](https://www.bluegreenowner.com/home)
A timeshare-club owner portal (points booking, registration flow, "remember me," max-2-concurrent-session limit) — included as the "big legacy timeshare" data point, but its capability set (points balance, book with points, rewards referrals) doesn't map cleanly onto a weekly-rental-and-sales brokerage; noted for completeness per the brief, not recommended as a pattern source.

### Brokerage CRM / IDX platforms (agent-backend ↔ consumer-search split)

**kvCORE / BoldTrail** (Inside Real Estate) — [Agent-facing overview](https://s.insiderealestate.com/kvcore-platform-agents/) · [Login/dashboard guide](https://loginsphire.com/kvcore-login/) · [Luxury Presence review](https://www.luxurypresence.com/blogs/kvcore-review/) · [InboundREM review](https://inboundrem.com/kvcore-kunversion-pros-cons/)
Unusual among the exemplars: **one login, two experiences.** The agent's dashboard (Smart CRM, Activity Feed, Lead Engine, Web & IDX site editor, Marketing Autopilot, built-in CMA tool) *is* the same account that configures the public-facing IDX website consumers browse. There is no independent "consumer account" identity in kvCORE itself — behavior on the public site (listings viewed, saved searches, return visits) flows back into the agent's CRM as tracked activity automatically, and the agent edits the consumer site from inside their own dashboard's "Web & IDX" tab. Reviewers (Luxury Presence, InboundREM) consistently flag that the **IDX website layer is templated and thin** — "almost everybody in your area will be using the exact same widgets… your page will look exactly the same as the other sites," which reviewers tie to duplicate-content SEO penalties.

**Follow Up Boss** — [Webhooks guide](https://docs.followupboss.com/reference/webhooks-guide) · [Review](https://aiandrealtors.com/review-followupboss) · [kvCORE vs. FUB comparison](https://ustechautomations.com/resources/blog/follow-up-boss-vs-kvcore-real-estate-2026)
Deliberately **not** an IDX/website product — "hub and spoke": FUB is the agent-facing lead inbox and pipeline (unified inbox across Zillow/Realtor.com/paid sources, Action Plans, Smart Lists, two-way texting), and it *integrates with* a separate IDX website (Real Geeks, Showcase IDX, Sierra Interactive) via API to pull in consumer-side behavioral signals (saved listings, saved searches) onto the lead's timeline. There is still no independent "consumer account" in FUB itself — the consumer-facing account lives entirely in whichever IDX product is bolted on. Useful proof point that **"agent inbox" and "consumer saved-listings surface" are separable products**, exactly the seam OSEAD should keep.

**Real Geeks** — [Lead Assignment](https://support.realgeeks.com/lead-assignment) · [Geographic Round Robin](https://support.realgeeks.com/geographic-round-robin) · [Custom CRM settings](https://support.realgeeks.com/customize-your-crm)
Best-documented **lead-routing** mechanics of the group, i.e. how a public inquiry becomes "assigned inventory" for one agent: **Round Robin** (rotate evenly across a named agent group, with per-agent availability toggles), **Lead Ponds** (a shared, claimable pool instead of auto-assignment), **geographic routing** (route by the county/state the lead searched in, then round-robin within that group), and **idle reassignment** (auto-move a lead to the next agent or a pond if not contacted within a set window). This is the concrete mechanism behind "assigned inventory" in the brief's coverage ask — OSEAD's demo version can be as simple as a static `agentId` field on a seeded inquiry record, but the naming (pond vs. round-robin vs. geo) is useful vocabulary for the UI copy.

**Sierra Interactive** — [API overview](https://help.sierrainteractive.com/helpcenter/unlock-new-opportunities-with-the-sierra-api)
Agent-facing endpoints: add/update/find leads, **retrieve saved listings**, find agents, log property views, submit showing/info requests — i.e. the guest-side "saved listings" and "request a showing" actions are *API objects the agent's system reads*, not a separate portal UI Sierra documents publicly. Consistent with the pattern above: consumer actions are data the agent-side product consumes, not a fully independent consumer product.

**BoomTown** — [Developer docs](https://developer.boomtownroi.com/)
Same shape as Follow Up Boss/Sierra (leads/users/properties/transactions, OAuth2) — included for completeness per the brief; no distinguishing consumer-portal pattern beyond the others.

### Boutique / luxury brokerage client portals (agent ↔ buyer-seller split, no IDX baggage)

**Compass One** — [Product page](https://one.compass.com/compass-one-experience-desktop/sellers-rsefg) · [Launch announcement](https://www.compass.com/newsroom/press-releases/6rnUy5QFL9thn6uW7bQSiG/) · [HousingWire coverage](https://www.housingwire.com/articles/compass-one-portal-clients-listings/) · [Inman review](https://www.inman.com/2025/02/28/compass-one-puts-clients-at-true-north-tech-review/)
The closest fit to "boutique brokerage, not heavy IDX." **Agents invite clients in** (no independent signup) to a shared, transaction-scoped dashboard: buyers get a "Collection" of saved/rejected homes with commentary, tour requests + schedule, live CMAs, a chat thread with the agent, a step-by-step transaction timeline, and a documents library (offers, disclosures, appraisals). Sellers get a parallel view (showings record, open-house calendar, documents, timeline). Explicitly framed by Compass as increasing agent stickiness post-NAR-settlement (buyer-agreement e-sign is a built-in step) — the account exists to keep the relationship inside Compass's ecosystem rather than leaking to Zillow/Redfin. No independent consumer marketing site is implied; the portal only exists once an agent relationship starts, which is a materially different onboarding model than kvCORE/Real Geeks' "anonymous IDX visitor signs up."

**RealScout** — [Pricing/plans](https://learn.realscout.com/pricing/) · [Agent overview](https://learn.realscout.com/agents/) · [Client-experience help center](https://support.realscout.com/en/collections/14471499-realscout-client-experience) · [Contact/homebuyer help center](https://support.realscout.com/en/collections/14471498-help-for-your-contacts)
Positions itself explicitly as **not an IDX website** — "a database nurture hub" layered over an agent's real MLS feed. Consumer side (their term: "contact"/"homebuyer account"): branded search under the agent's headshot/logo, mark listings **Interested/Uninterested** (persisted, editable later), saved Client Searches with configurable alert cadence, a message-your-agent tab that can attach specific saved listings, room-by-room photo browsing, and commute-time calculation. Agent side: a live activity feed of every save/view/showing-request, "Scout Score" intent scoring, and CRM/lead-source integrations (explicitly integrates with Follow Up Boss and Zillow rather than replacing them). The Interested/Uninterested binary plus a persistent, editable "why I passed" state is a nicely minimal saved-listing shape worth mirroring for a `guest` role's local storage.

### "Continue booking externally" handoff patterns (deep link → magic link → SSO)

**Tier 1 — Query-string deep links (no auth, no backend, ship this).**
[Mews Booking Engine deeplinks](https://docs.mews.com/booking-engine-guide/booking-engine-standalone/deeplinks) — URL query params select property/room/rate/currency and can jump straight to a booking step (`mewsRoute=rates`). [Skipper Deep Link API](https://docs.skipperhospitality.com/docs/deep-linking/deep-link-api/) — same idea via query params (`sbe_startDate`, `sbe_endDate`, `sbe_openBE=true` to auto-run the search) or HTML `data-*` attributes on a CTA button. [WPRentals "Affiliate Link"](https://help.wprentals.org/article/add-a-redirect-url-instead-of-book-now-button/) — the plainest version: a single URL field on a listing that replaces the theme's own "Book Now" action with a redirect to Airbnb/Vrbo/any external booking URL. [Flip.to booking-engine-URL templating](https://docs.flip.to/docs/platform/mission-control/booking-engine-url) — token-templated URL (`?aDate={start-date,format=MM/dd/yyyy}&adults={adults}&promo={promo-code}`) built once per hotel, then filled per-click. **This is the direct pattern for OSEAD's "Check availability" / "Continue to book" CTA**: build the external booking URL from the property's own frontmatter (dates, party size, a stable listing ID) as a query string — zero session, zero auth, matches "site owns experience, doesn't own the calendar."
**Tier 2 — Magic links (passwordless re-entry, not booking-specific).** [Ping Identity explainer](https://www.pingidentity.com/en/resources/blog/post/what-is-magic-link-login.html) · [LoginRadius guide](https://www.loginradius.com/blog/identity/passwordless-authentication-magic-links) · [Bento implementation guide](https://bentonow.com/posts/magic-links-guide) · [MojoAuth security deep dive](https://mojoauth.com/blog/are-magic-links-secure-technical-deep-dive). Consensus best practice: single-use, 10–15 minute TTL tokens (5 min for step-up/reauth), hashed at rest, invalidated on first click, rate-limited per request, with a visible "resend" affordance and a device-binding option that degrades gracefully (don't hard-block a desktop-request/mobile-click split). This is the realistic upgrade path if OSEAD ever wires outbound email (Resend/Mailchannels is already flagged as optional in `docs/PLAN.md` Phase 3) — a magic link could replace the current shape-only `/login` with something that actually re-opens a saved guest session, without standing up password storage.
**Tier 3 — SSO/token handoff to a third-party booking engine (document, don't build).** [Sabre SynXis CRM-Login SSO](https://developer.synxis.com/commerce/crm_sso) · [SSO reference](https://developer.synxis.com/commerce/sbe_sso/references) · [Setup guides (SAML + custom OAuth, brand-site-initiated flow)](https://developer.synxis.com/commerce/sbe_sso/setup-guides) · [Brand-site flow detail](https://developer.synxis.com/brand-site-flow). SynXis's pattern is the cleanest documented example of "marketing site hands off a signed-in guest to an external booking engine": the brand's CRM calls a Login API to get a short-lived `access_token`, then **POSTs it as a hidden form field (`session`)** to the booking engine's URL, alongside the deconstructed query params from the original booking link (`backurl`). SynXis explicitly supports SAML and custom OAuth for this, with a documented "brand-site-initiated" flow (logged-in guest clicks an SBE link → brand site kicks off SSO with the booking engine as the SAML `RelayState` → guest lands on the booking engine already authenticated). This is real, working enterprise plumbing — but it requires a specific IdP contract with a specific booking vendor per property, exactly the kind of thing this wave's non-goals list (`docs/research/accounts-rbac-feature.md`: "Live OAuth / Clerk / Auth0 wiring — document plug shape only") already rules out building. Worth one line in OSEAD's own docs as "here's what a real SSO handoff looks like if a future integrator needs it," never worth building against a specific vendor now.

### Lead-assignment vocabulary (for "assigned inventory" copy)

[Pipedrive real-estate lead routing guide](https://www.pipedrive.com/en/blog/real-estate-lead-routing) · [iHomefinder smart routing guide](https://www.ihomefinder.com/blog/agent-and-broker-resources/lead-routing-for-real-estate/) — round-robin (even rotation), first-available, skill-based, geographic, and "sink or swim" (round-robin first, drops to a shared pond if untouched past a deadline) are the five named patterns every CRM in this space reduces to. OSEAD's demo doesn't need live routing logic — a static `assignedAgentId` on each seeded inquiry is enough — but this vocabulary is the right frame for any future "how would a real brokerage route these" doc note.

## What NOT to copy

- **Full IDX/MLS search dashboards** (kvCORE Web & IDX editor, Real Geeks/Sierra Interactive/BoomTown's whole product category). These exist to solve MLS data-feed licensing and SEO-scale property search — problems OSEAD's Markdown-collection inventory doesn't have. Reviewers themselves (Luxury Presence, InboundREM) flag the templated-IDX-page approach as a duplicate-content SEO liability, not just "more than we need." **Don't build a search/filter system that pretends to be MLS-backed.**
- **Full PMS owner/financial modules** (Vacasa's revenue dashboard + 1099 generation, Twiddy's homeowner performance portal, Bluegreen's points-balance/booking engine). These require a real payments/tax pipeline behind them — exactly the "no mandatory new CMS/DB" and "booking stays external" constraints this wave already rules out. A `guest` or `agent` role in OSEAD should never show real money.
- **Independent consumer signup funnels bolted onto a CRM** (kvCORE's "anonymous IDX visitor" model, BoomTown/Sierra's paid-lead-gen positioning). OSEAD's guest account should look more like Compass One's model — an account that becomes useful *once you're already inquiring about a property on this site* — not a acquisition funnel with its own marketing site.
- **Vendor-specific SSO/token handoffs** (SynXis SAML/OAuth integration, Mews' hosted-booking-engine session model). Real, but contractually vendor-specific; building against one now would be dead code for every other deployer of this template. Document the *shape* (tier 3 above), build only tier 1 (deep link).
- **Native mobile apps for either role** (Twiddy app's trip-board group voting, Vacasa Homeowner app's push notifications). Already a non-goal in `docs/PLAN.md` Phase 5 ("Native mobile apps") — nothing here changes that.
- **Lead-routing automation engines** (Real Geeks' Round Robin/Lead Pond configuration UI, kvCORE's Smart Campaigns triggered by behavior). The *concept* (assignedAgentId) is worth keeping; the *configurable-rules UI* is a SaaS feature for a multi-agent brokerage operating this at scale, not a demo template concern.

## Recommendations for OSEAD demo (offline seed accounts)

All of this extends the existing `sessionStorage` + `DemoRole` contract in `src/lib/demo-account.ts` — no new persistence layer, no CMS, no DB, matching the AGENTS.md "keep backend light" rule and this feature's own non-goals list.

1. **Widen `DemoRole` to `"admin" | "agent" | "guest"`** (drop the generic `"user"` — every exemplar above names the consumer role explicitly, and `staff.ts` already gives OSEAD a named-person seed for `agent`). Keep `roleForEmail()`'s single-admin-email pattern, add a small `agent` allowlist sourced from `demoStaff` (e.g. `jonah-reed@osead.demo` → agent), and default anything else to `guest`.
2. **Seed the `guest` role's local storage the way `RealScout`/`Twiddy` shape it**: a `savedListingSlugs: string[]` (RealScout's Interested/Uninterested binary, simplified to a toggle) and an `inquiries: { propertySlug, submittedAt, status }[]` mirroring what the existing `/contact` inquiry form already posts to `functions/api/contact.ts` — just persist the client's own copy of what they sent, exactly like `demo-account.ts` already persists its own session, no server round-trip needed.
3. **Seed the `agent` role's home screen as an inbox + inventory filter, not an AdminShell clone**: reuse `demoStaff` for identity, add a static `assignedAgentId` field to each seeded inquiry (Real Geeks' vocabulary: this is the "already round-robin'd" state, not a live router), and show the agent only inquiries where `assignedAgentId` matches their staff id, plus a read-only slice of `properties`/`markets` filtered to whatever the demo wants to call "their listings" (e.g. by market or by a new frontmatter `agentId` field — confirm against `docs/specs/property-content.md` before adding a field).
4. **Implement "continue booking externally" as a pure URL builder (tier 1 only)**: a small `buildExternalBookingUrl(property, { checkin, checkout, guests })` helper that appends a query string to a `externalBookingUrl` (or reuse `property-content.md`'s existing external-link field if one exists) — no session, no token, matches Mews/Skipper/WPRentals' pattern exactly. Document the magic-link (tier 2) and SSO-handoff (tier 3) patterns above in a code comment or follow-up doc as the explicit upgrade path, per the `ponytail:` convention already used in `functions/api/login.ts`.
5. **Do not add a lead-routing UI, IDX search, or owner financials this wave** — see "What NOT to copy" above. If a future ticket wants "round robin," the vocabulary and mechanics are already documented here (Real Geeks section) to save re-research.

## Top 5 UX must-haves

**Agent:**
1. **One inbox, filtered to "mine."** Every agent-side exemplar (FUB Smart Lists, kvCORE Activity Feed, Real Geeks claimed leads) opens on assigned inquiries, not a dashboard of everything — the agent's first screen should be their own inquiry queue, not the site's.
2. **Visible assignment state.** Whether it's round-robin, a pond, or a static seed, the agent should be able to see *why* an inquiry is theirs (Real Geeks names this explicitly in the UI) — even a static "Assigned via: Market rotation" label beats silence.
3. **Behavioral context on each lead**, not just contact info — which listing(s) they saved/asked about (RealScout's live activity feed, kvCORE's behavioral tracking) turns a bare inquiry into something an agent can act on immediately.
4. **A visible "my inventory" slice**, scoped by market or assignment, not the full site catalog — mirrors every exemplar's "assigned listings" framing rather than a generic admin-style browse.
5. **No content-editing surface bleeding in from `AdminShell`.** Every exemplar keeps "manage my leads" and "edit the site" as separate concerns (even kvCORE, which shares a login, separates them into distinct tabs) — the agent role should never see site-wide admin tools.

**Guest:**
1. **Saved listings that persist across visits without forcing an account upfront** — Twiddy's guest trip boards, Compass One's Collections, and RealScout's Interested/Uninterested all treat "save for later" as the entry point, with a full account mattering only once they're transacting.
2. **Own inquiry/reservation history, scoped to just them** — every exemplar (Vacasa reservation view, Compass One's transaction timeline, RealScout's message thread) shows the guest exactly their own status, nothing about other guests or the brokerage's book of business.
3. **A clear, low-friction handoff moment to the external booking step** — Twiddy's guest login exists specifically to sign the lease and pay; the account's job ends where the external transaction begins, and the UI should say so plainly (a "continue to book" CTA, not a fake in-site checkout).
4. **A visible line to a human agent, not just a form.** RealScout's message-your-agent tab and Compass One's chat thread both keep the assigned agent one click away from any saved listing — worth mirroring even as a "email this agent about this listing" mailto/contact-form link in the demo.
5. **No homeowner/financial data bleeding into the guest view.** Vacasa's owner revenue dashboard and Twiddy's homeowner portal are completely separate products from the guest experience — OSEAD's `guest` role should never be one misconfigured check away from seeing anything admin- or agent-facing.
